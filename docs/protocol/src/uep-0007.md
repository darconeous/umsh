This UEP defines how packets are secured: the keys two nodes or the members
of a group derive, how a packet's MIC and encryption are computed, frame
signatures, frame counters and replay detection, acknowledgments, and the
procedure a node follows to receive a packet.

## Primitives {#primitives}

- **Ed25519** ([RFC 8032](https://www.rfc-editor.org/rfc/rfc8032)): node
  keys and signatures.
- **X25519** ([RFC 7748](https://www.rfc-editor.org/rfc/rfc7748)): key
  agreement.
- **HKDF-SHA256** ([RFC 5869](https://www.rfc-editor.org/rfc/rfc5869)): key
  derivation.
- **AES-SIV** ([RFC 5297](https://www.rfc-editor.org/rfc/rfc5297)) with
  AES-256: authentication and encryption. Its S2V function is built on
  AES-CMAC ([RFC 4493](https://www.rfc-editor.org/rfc/rfc4493)).

## Keys {#keys}

### Address Validation {#address-validation}

A node accepts an address only if it is the canonical encoding of a point on
the Ed25519 curve: decoding it and encoding the point again yields the same 32
bytes. A node rejects any other address before using it.

### Key Conversion {#key-conversion}

A node uses its Ed25519 keypair for key agreement as well as signing, through
the standard conversion to X25519:

- **Private key**: the first 32 bytes of the SHA-512 hash of the Ed25519
  private key, clamped as X25519 clamps a scalar.
- **Public key**: the Montgomery `u`-coordinate of the Ed25519 point,
  `u = (1 + y) / (1 − y)` over the field of Curve25519.

### Pairwise Keys {#pairwise-keys}

Two nodes with addresses `PK_a` and `PK_b` derive a pair of keys that secures
the unicast traffic between them:

```text
ss    = X25519(local X25519 private key, remote X25519 public key)
okm   = HKDF-SHA256(ikm = ss,
                    salt = "UMSH-PAIRWISE-SALT",
                    info = "UMSH-UNICAST-V3" ‖ min(PK_a, PK_b) ‖ max(PK_a, PK_b),
                    L = 64)
K_mic = okm[0..32]
K_enc = okm[32..64]
```

`min` and `max` compare the two addresses as byte strings, so both nodes
derive the same keys. A node that computes an all-zero `ss` rejects the peer's
address.

`okm` is the AES-SIV key `K` of [RFC 5297](https://www.rfc-editor.org/rfc/rfc5297): `K_mic` is its S2V half and `K_enc`
its CTR half.

### Group Keys {#group-keys}

A group is defined by a 32-byte **group key**, as [UEP-0008](uep-0008.md)
defines. From it, every member derives:

```text
group_id   = HKDF-SHA256(ikm = group key, salt = "UMSH-CHAN-ID", info = "", L = 32)
group_hint = group_id[0..2]

okm   = HKDF-SHA256(ikm = group key,
                    salt = "UMSH-MCAST-SALT",
                    info = "UMSH-MCAST-V2" ‖ group_hint,
                    L = 64)
K_mic = okm[0..32]
K_enc = okm[32..64]
```

#### Group ID {#group-id}

The **group ID** names a group without disclosing its key. No packet field
carries it. A [frame signature](#frame-signatures) covers it, which binds the
signature to the group.

#### Group Hint {#group-hint}

The **group hint** is the first two bytes of the group ID, carried in a
packet's `GROUP` field. Like a [node hint](uep-0004.md#node-hint), it is a prefilter: distinct group
keys can share one, and a node learns which group a packet belongs to by
verifying its MIC.

### Group Unicast Keys {#group-unicast-keys}

The payload of a group unicast is secured with keys that require both the two
nodes' pairwise keys and the group's keys:

```text
K_mic = K_mic(pairwise) XOR K_mic(group)
K_enc = K_enc(pairwise) XOR K_enc(group)
```

Its address block is encrypted with the group's `K_enc` alone, as
[Group Unicast Address Block](#group-unicast-address-block) defines.

## Packet Protection {#protection}

A packet that carries SECINFO is authenticated by its MIC, and encrypted when
the SCF's `E` bit is set. Its keys depend on its packet type:

| Packet type | Keys |
|---|---|
| Unicast | [Pairwise keys](#pairwise-keys) |
| Multicast | [Group keys](#group-keys) |
| Group unicast | [Group unicast keys](#group-unicast-keys) |

### Associated Data {#associated-data}

The **associated data** (AAD) covers the fields that do not change in
transit. It is the packet's header fields in wire order, except that:

- `FHOPS` is omitted, and the FCF enters with its `H` bit cleared.
- Static options are re-encoded as described below, and dynamic options are
  omitted.
- The options are followed by the terminator `FF FF`, even when there are no
  static options.
- Group unicast's `DST ‖ SRC` follows the terminator in plaintext, whether or
  not it is encrypted on the wire.

| Packet type | AAD |
|---|---|
| Broadcast | `FCF ‖ SRC ‖ options ‖ FF FF` |
| MAC ack | `FCF ‖ options ‖ FF FF` |
| Unicast | `FCF ‖ DST ‖ SRC ‖ SECINFO ‖ options ‖ FF FF` |
| Multicast | `FCF ‖ GROUP ‖ SECINFO ‖ options ‖ FF FF` |
| Group unicast | `FCF ‖ GROUP ‖ SECINFO ‖ options ‖ FF FF ‖ DST ‖ SRC` |

Addresses enter as the packet carries them: a [node hint](uep-0004.md#node-hint), or a full address
where the packet carries one. A broadcast has no MIC, and its AAD is used only
by a frame signature.

Each static option enters as a record of its absolute number, its length,
and its value, in order of increasing number:

```text
+----------+----------+-------+
|  NUMBER  |  LENGTH  | VALUE |
+----------+----------+-------+
    2 B        2 B     variable
```

No static option can begin with `FF FF`, since option 65535 is dynamic, so
the terminator fixes where the options end.

### MIC {#mic}

The packet's **plaintext** `S2` is everything between its options and its
MIC, in plaintext form, except a group unicast's address block, which enters
the AAD instead:

| Packet type | `S2` |
|---|---|
| Unicast | `PAYLOAD [‖ SIG]` |
| Multicast | `SRC ‖ PAYLOAD [‖ SIG]` |
| Group unicast | `PAYLOAD [‖ SIG]` |

The sender computes the synthetic IV

```text
V = S2V(K_mic, AAD, S2)
```

as [RFC 5297 §2.4](https://www.rfc-editor.org/rfc/rfc5297#section-2.4) defines, with the AAD as the one associated-data component.
The packet's MIC is the first bytes of `V`, as many as the SCF's MIC size
gives. The computation is the same whether or not the packet is encrypted.

A receiver compares a MIC in constant time.

### Encryption {#encryption}

When `E` is set, the sender encrypts `S2` with AES-256-CTR under `K_enc`. The
16-byte initial counter is built from the MIC and SECINFO as carried:

```text
IV     = the first 16 bytes of (MIC ‖ SECINFO ‖ 16 zero bytes)
IV[8]  = IV[8]  & 0x7F
IV[12] = IV[12] & 0x7F
```

The counter increments as a 128-bit big-endian integer. With a 16-byte MIC,
`IV` is [RFC 5297](https://www.rfc-editor.org/rfc/rfc5297#section-2.6)'s initial counter `Q`, and the packet is the output of
AEAD_AES_SIV_CMAC_512 with the MIC moved to the end.

### Group Unicast Address Block {#group-unicast-address-block}

When `E` is set, a group unicast's `DST ‖ SRC` is encrypted with AES-256-CTR
under the group's `K_enc`, with the same `IV`:

```text
ENC_DST_SRC = AES-256-CTR(group K_enc, IV, DST ‖ SRC)
```

The sender computes the MIC over the plaintext addresses first, then encrypts
the address block. A receiver holding the group key decrypts the block from
the MIC before it knows the payload keys, derives them from the recovered
`SRC`, and then verifies the MIC, which covers the addresses.

### MIC Size {#mic-size}

A shorter MIC saves bytes and weakens forgery resistance in proportion. A
sender SHOULD choose by how long the keys stay in use and what they protect:

- **16 bytes** for long-term identities, whose keys may stay in use for
  years.
- **8 bytes** for general traffic.
- **4 bytes** for keys discarded soon, such as those of a
  [forward secrecy session](uep-0009.md).

## Frame Signatures {#frame-signatures}

A **frame signature** is an Ed25519 signature by the source's key over the
bytes the MIC covers. It attributes a frame to that key. A group MIC alone
shows only that the sender holds the group key.

A frame with SECINFO is signed by setting the SCF's `D` bit and placing a
64-byte `SIG` after the payload, as the last part of `S2`. A broadcast is
signed with the [Frame Signature option](#frame-signature-option). A MAC ack
is never signed.

### Signature Input {#signature-input}

```text
signature_input = "UMSH-SIG" ‖ AAD ‖ [group_id] ‖ plaintext
```

- `"UMSH-SIG"` is the 8 ASCII bytes `55 4D 53 48 2D 53 49 47`.
- `AAD` is the frame's [associated data](#associated-data), with `D` set.
  On a broadcast, the Frame Signature option enters with its 64 signature
  bytes replaced by zeros.
- `group_id` is the [group ID](#group-id), on multicast and group unicast
  only.
- `plaintext` is `S2` without `SIG`, or a broadcast's payload.

### Frame Signature Option (0) {#frame-signature-option}

```text
+---------------+-----------+
| FRAME COUNTER | SIGNATURE |
+---------------+-----------+
      4 B           64 B
```

The option signs a broadcast. `FRAME COUNTER` is drawn from the source's
[counter](#frame-counters). A sender MUST NOT include the option on a packet
type that carries SECINFO, where a receiver ignores it, or include more than
one. A broadcast with more than one is treated as unsigned. A value of any
other length is treated as an unrecognized option.

### Verification {#signature-verification}

A receiver verifies a signature against the source's address:

- On a unicast or group unicast, the address whose keys verified the MIC.
- On a multicast or broadcast, `SRC` when the frame carries a full address,
  or else the address of the one known peer whose node hint matches `SRC`.

On a multicast or group unicast, the signature input takes the group ID of
the group key that verified the MIC.

A receiver verifies with the cofactorless equation of
[RFC 8032 §5.1.7](https://www.rfc-editor.org/rfc/rfc8032#section-5.1.7), and
rejects a signature whose `S` is not less than the group order or whose `R`
or public key has small order.

- A frame whose signature verifies is attributed to that address, and its
  counter is judged as [Signed Frames](#signed-frames) defines.
- Any other signed frame is processed as an unsigned frame from the same
  source. A failed signature is not by itself grounds to discard a frame,
  since a hint can match a different peer than the one that signed it.

A frame whose MIC fails is discarded before its signature is considered.

## Frame Counters {#frame-counters}

A node address draws the counters of every frame it secures or
signs—unicast, group unicast, multicast, and signed broadcast—from one
sequence, and MUST NOT let that sequence go backward. A receiver judges every
frame it authenticates as one peer's, by MIC or by signature, against one
baseline for that peer.

The [salt](uep-0005.md#salt), when present, is two random bytes that vary a
packet's IV. A receiver MUST NOT rely on AES-SIV's resistance to nonce reuse
in place of replay detection.

### Replay Detection {#replay-detection}

A receiver judges a counter against the highest it has accepted from the
peer:

```text
delta = (received − highest accepted) mod 2^32
```

- If `delta` is zero, or greater than the **forward window** and the frame
  is not in the backward window below, the frame is rejected. The suggested
  forward window is 172800.
- A receiver MAY keep a **backward window** of counters just behind the
  highest accepted, so that frames arriving out of order are not lost. The
  suggested backward window is 8. A frame in the backward window is a replay
  if the receiver has already accepted a frame with its counter, whatever its
  MIC, and is accepted otherwise.
- A receiver never accepts a frame behind the highest accepted counter if
  that counter was last advanced more than 5 minutes earlier.
- The first frame accepted from a peer sets its **baseline**. A receiver never
  accepts a frame behind the baseline.

A sender SHOULD NOT have more packets awaiting acknowledgment from one peer
than the suggested backward window, so that a retransmission of the earliest
still falls inside the window.

### Signed Frames {#signed-frames}

A frame whose signature verifies is judged against its signer's counter. A
signed broadcast has no MIC, so the receiver recognizes it by its counter and
the first 16 bytes of its signature.

- **Known peer**: the frame is judged against the peer's baseline, as its
  unicast traffic is, and an accepted frame advances it. A frame behind the
  baseline or outside the window MAY prompt
  [resynchronization](#counter-resynchronization), unless the receiver
  recognizes it as a late copy of a frame it accepted.
- **Stranger**: a frame signed by an address that is not a known peer's is
  first contact. Later frames from that address are judged in a window the
  receiver keeps for it, and a frame outside that window is discarded without
  resynchronization.
  - A receiver MAY discard a stranger's window when it is idle or memory is
    short.
  - A receiver SHOULD bound how many strangers' windows new signers displace.
    The suggested bound is 4 every 10 minutes. A frame from a new signer
    after the bound is spent is judged as an
    [unsigned multicast](#unsigned-multicast) is.

### Unsigned Multicast {#unsigned-multicast}

A multicast without a verified signature could have come from any member of
the group, whatever its `SRC` says. A receiver judges it by duplicate
suppression alone, keyed by its MIC: a multicast whose MIC matches one
already accepted is a replay, whatever dynamic options it carries.

An unsigned multicast MUST NOT change any counter state kept for the source
it names.

### Counter Persistence {#counter-persistence}

A node MUST NOT reuse a counter value across restarts. It persists its counter,
or advances it on startup past every value it may have used. It MUST advance
it by less than the suggested forward window, or every peer would have to
resynchronize.

A node MUST persist each known peer's baseline and restore it on startup, or
it would accept a replay of that peer's earlier frames as first contact.

- The persisted baseline MAY lag the live one, so that writes can be batched.
  A node SHOULD write a peer's baseline once it has accepted 16 frames from
  that peer since the last write.
- Before a deliberate restart, a node SHOULD write every baseline that has
  changed since its last write.

### Counter Resynchronization {#counter-resynchronization}

A frame from a known peer whose counter falls outside the window, or in an
unspent slot of the backward window past the 5-minute bound, shows that the
two nodes disagree about the peer's counter. A frame the backward window
records as spent is a replay, and one the receiver recognizes as a late copy
of a frame it accepted prompts nothing.

For any other such frame, the receiver MAY establish a new baseline with one
of the exchanges below. It SHOULD send at most one probe to a peer every 5
seconds, and never sends one in answer to a Verify Frame or Frame Verified.

**When the frame requested an acknowledgment**, the receiver, the
**requester**, holds the frame without acknowledging it and sends
[Verify Frame](#verify-frame) to the peer, naming the frame with an
[Ack MIC option](#ack-mic-option). The peer, the **responder**:

1. Matches the option against the packets it sent to the requester that
   await acknowledgment. If none matches, it ignores the Verify Frame.
2. Stops retransmitting the matched packet and answers with
   [Frame Verified](#frame-verified).
3. Treats the matched packet as acknowledged when Frame Verified is
   acknowledged, and as failed if it never is.

The responder processes a Verify Frame whose counter is outside its window
for the requester, since the match shows the request is fresh, and adopts
that counter as the requester's baseline once Frame Verified is acknowledged.
A Verify Frame whose counter is inside the window is judged by the ordinary
replay rules.

When a Frame Verified echoes the nonce of a Verify Frame for a frame the
requester still holds, the requester adopts its counter as the peer's
baseline, delivers the held frame, and acknowledges Frame Verified. That
acknowledgment stands for the held frame too. A requester that no longer
holds the frame discards Frame Verified without acknowledging it. The
requester MUST choose nonces so that an earlier Frame Verified cannot match a
later Verify Frame.

A probe is carried the way the frame that prompted it arrived, as
[UEP-0005 §response-carriage](uep-0005.md#response-carriage) defines.

**When the frame did not request an acknowledgment**, the receiver MAY send
an [Echo Request](uep-0006.md#echo-request) carrying a nonce, and discards the
frame. An Echo Response that echoes the nonce sets the peer's baseline to its
counter, unless a frame accepted from the peer since the probe was sent has
already advanced it. When the frame is itself an Echo Request, the receiver
answers it before sending its own probe, and only when it sends one; the
request is not delivered and moves no baseline.

### Verify Frame (12) {#verify-frame}

Asks the destination to vouch for a frame it sent to the requester. Carried by unicast and group unicast only.

| Field | Size | Description |
|---|---:|---|
| Nonce | 4 bytes | Chosen by the requester |

The packet carrying it MUST include an [Ack MIC option](#ack-mic-option)
naming the frame, and SHOULD NOT request an acknowledgment. A responder ignores
a Verify Frame without the option. The option names a frame to verify here,
not an acknowledgment.

### Frame Verified (13) {#frame-verified}

Answers a Verify Frame naming a packet the responder sent and is waiting to
have acknowledged. Carried by unicast and group unicast only.

| Field | Size | Description |
|---|---:|---|
| Nonce | 4 bytes | Copied from the Verify Frame |

The packet carrying it MUST request an acknowledgment.

## Acknowledgments {#acknowledgments}

A unicast or group unicast that requests an acknowledgment (`UNAR` or `GUAR`)
is acknowledged by its destination when the destination accepts it as new.
Repeaters forward acknowledgments and never generate them.

### Ack Tag {#ack-tag}

A [MAC ack](uep-0005.md#mac-ack) carries two values:

```text
ack_mic = MIC[0..4]
ack_tag = S2V(K_mic, AAD_ack, V, ack_mic)[0..4]
```

- `MIC` and `V` are the acknowledged packet's on-wire MIC and full 16-byte
  synthetic IV.
- `K_mic` is the key that secured the acknowledged packet: the pairwise key,
  or the group unicast key.
- `AAD_ack` is the ack's own [associated data](#associated-data).

`ack_mic` lets the original sender, and any node that saw the original
packet, match the ack to it. It is public, and authenticates nothing.
`ack_tag` authenticates the ack and its static options; only the two
endpoints can produce it. The original sender matches an ack by `ack_mic`,
then verifies `ack_tag`, and discards an ack whose tag fails.

### Ack MIC Option (8) {#ack-mic-option}

A 4-byte `ack_mic`. A packet carrying it acknowledges the packet it names, as
a MAC ack would. A destination answering an acknowledgment-requested packet
with a unicast or group unicast of its own MAY include the option, whether or
not it also sends a MAC ack. The original sender takes whichever arrives
first, and accepts the option only on a packet authenticated as coming from
the destination of the packet it names.

On a [Verify Frame](#verify-frame), the option names a frame to verify, and
the original sender MUST NOT treat it as an acknowledgment.

### Duplicate Acknowledgments {#duplicate-acknowledgments}

A receiver that rejects a packet as a replay MAY acknowledge it again if it
requests an acknowledgment, is authenticated, and its counter is no more than
8 behind the highest accepted counter from its sender:

```text
(highest accepted − received) mod 2^32 ≤ 8
```

A receiver MUST NOT acknowledge a replay farther behind. Acknowledging a
duplicate does not accept it again: it MUST NOT change the sender's counter
state, and the payload is not delivered again.

## Receive Procedure {#receive-procedure}

A node processes a packet in these steps, however the packet reached it:

1. **Parse.** Discard a packet that [UEP-0005](uep-0005.md) says to discard.
2. **Acknowledgment.** A MAC ack is matched against the packets this node
   awaits acknowledgment for, as [Ack Tag](#ack-tag) defines, and goes no
   further.
3. **Address.** Continue with a broadcast, a packet whose destination hint
   matches this node's node hint, or a packet whose group hint matches a
   group this node belongs to. Stop otherwise.
4. **Authentication.** A broadcast skips this step. For any other packet,
   try each candidate key that could have secured it, and stop if none
   verifies the MIC:
   - Unicast: the pairwise keys of each known address whose node hint
     matches `SRC`, or of `SRC` itself when it is a full address.
   - Multicast: the keys of each group whose group hint matches.
   - Group unicast: for each group whose group hint matches, decrypt the
     address block. Continue with that group only if `DST` matches this
     node's node hint, and try the group unicast keys of each candidate
     address for `SRC`.
5. **Options and payload.** Discard a packet whose payload type its packet
   type may not carry, or that carries a delivery-critical option this node
   does not recognize, as [UEP-0005](uep-0005.md#criticality) defines.
6. **Replay.** Verify any frame signature, and judge any frame counter as
   [Frame Counters](#frame-counters) defines.
   - A duplicate may be acknowledged again, as
     [Duplicate Acknowledgments](#duplicate-acknowledgments) allows, and goes
     no further.
   - A Verify Frame, Frame Verified, or Echo Request outside the window is
     handled as [Counter Resynchronization](#counter-resynchronization)
     defines.
   - Any other packet replay detection rejects is discarded.
7. **Acceptance.** A node MAY decline a new acknowledgment-requested packet
   it has no room to hold, discarding it without acknowledging it and
   without recording its counter. Otherwise, the node records the counter,
   acknowledges the packet if it requests it and has no
   [source-route hops still pending](uep-0014.md#pending-route-ack), and
   delivers the payload.

A node processes a packet addressed to it whether or not the packet has
further hops to travel.

## Security Considerations {#security-considerations}

**Nonce misuse.** A sender that repeats a key, associated data, and
plaintext produces an identical packet, which reveals only the repetition.
A truncated MIC weakens this in proportion to the truncation, since the IV is
rebuilt from the truncated MIC and SECINFO.

**Low-order points.** Address validation and the check for an all-zero
shared secret keep a malformed address from forcing pairwise keys that every
peer would share.

**Acknowledgments.** A 4-byte ack tag is forged with probability 2<sup>−32</sup>
per attempt, only while the packet awaits acknowledgment, with no offline
check and a transmission per guess. A successful forgery makes the sender
treat an undelivered packet as delivered. Anyone who saw a packet can send
its `ack_mic`, so a node that only reads `ack_mic` treats it as a hint, never
as proof. An ack names neither endpoint, but anyone who saw the acknowledged
packet can link the ack to it.

**Group unicast.** Forging a group unicast, or reading an encrypted one's
payload, takes both the group key and the pairwise keys. Members of the group
can read an encrypted group unicast's address block.

**Unsigned multicast.** Any member of a group can send a multicast naming
any `SRC`. Once a receiver's duplicate suppression forgets a multicast, a
replay of it is accepted again.

**Signatures.** A group ID can be disclosed to let a third party
verify an unencrypted signed multicast without disclosing the group key. A
frame signed under a node hint can be verified only by a receiver that already
holds the sender's address.

**Counters.** A node whose persisted baseline lags the live one accepts,
after a restart, a replay of each frame it accepted since the last write. A
node with no baseline for a peer accepts a replay of any earlier frame from
it as first contact. A stranger's frame is accepted at face value once after
its window is discarded.

**Resynchronization.** A packet whose acknowledgment was lost can be
delivered twice, if a retransmission arrives after the receiver has
forgotten accepting it. Frame Verified shows only that the sender still
awaits an acknowledgment, not that the packet was never delivered.
