This UEP defines text messages: the payload that carries human-readable text
between nodes and to a group, its options, how messages are numbered and
fragmented, how replies, reactions, and edits refer to earlier messages, and
how a receiver asks for a message it missed.

## Payload {#payload}

A text message is a payload of [payload type](uep-0005.md#payload) 3:

```text
+--------------+---------+------+------+
| PAYLOAD TYPE | OPTIONS | 0xFF | BODY |
+--------------+---------+------+------+
      1 B        variable   1 B   variable
```

- `OPTIONS`: an [options block](uep-0003.md#options) of
  [text message options](#options), which may be empty.
- `0xFF`: the [end marker](uep-0003.md#end-marker), present only when a body
  follows.
- `BODY`: the message's text, as [Message Body](#body) describes.

A text message is carried by unicast, group unicast, or multicast, each with
or without an acknowledgment request where the packet type has one. A
broadcast does not carry one, and a receiver discards a text message that
arrives by broadcast, as [UEP-0005](uep-0005.md#compatibility) provides. A
node that receives text messages advertises the `TXT`
[capability](uep-0011.md#capabilities).

A receiver discards a text message whose options block is
[malformed](uep-0003.md#malformed).

## Conversations {#conversations}

A message belongs to a **conversation**, which decides how its messages are
numbered and how one refers to another:

- A **one-to-one conversation** is between two nodes, carried by unicast or
  by group unicast. The two nodes number their messages independently. A
  one-to-one conversation by group unicast on a group is distinct from the
  one by unicast between the same two nodes, and from the group conversation
  on that group, though the last two share key material.
- A **group conversation** is that of a group, carried by multicast. Every
  member numbers its own messages.

A message identifies its sender by the source of its packet. A unicast or
group unicast is authenticated to its source. A multicast is authenticated
only to the group, so its source is a claim, as
[UEP-0008](uep-0008.md#sender-attribution) explains, unless a
[frame signature](uep-0007.md#frame-signatures) attributes it.

## Options {#options}

| Number | Name | Value |
|---:|---|---|
| 0 | [Message Type](#message-type) | 0 or 1 bytes |
| 1 | [Sender Handle](#sender-handle) | UTF-8 string |
| 2 | [Message Sequence](#message-sequence) | 1 or 3 bytes |
| 3 | [Sequence Reset](#sequence-reset) | No value |
| 4 | [Regarding](#regarding) | 1, 2, or 4 bytes |
| 5 | [Editing](#editing) | 1 byte |
| 6 | [Background Color](#colors) | 3 bytes |
| 7 | [Text Color](#colors) | 3 bytes |
| 8 | [Group Resend](#group-resend) | No value |
| 9 | [Padding](#padding) | Any |

A receiver ignores an option it does not recognize, and an option whose value
it cannot decode.

Each option appears at most once unless its definition says otherwise. What a
receiver does with a repeated option depends on the option's role:

- **Identity, sequencing, and reference options**: Message Type, Message
  Sequence, Regarding, and Editing, and options of a later UEP that state
  they have this role. A repeat cannot be trusted, even when its value
  repeats, so the receiver treats the option as one it cannot decode.
- **Presentation options**: Sender Handle, Background Color, and Text Color.
  The receiver keeps the first occurrence and ignores the others.
- **Flags**: Sequence Reset and Group Resend. A repeat changes nothing.

A sender that sees its message delivered expects its body to be shown. A
receiver therefore displays a message that has a body, whatever it could not
interpret about it, and loses only the meaning of what it could not
interpret:

- A message whose Message Sequence it cannot decode is displayed as an
  unsequenced message.
- A message whose Message Type it does not recognize or cannot decode is
  displayed as a basic text message.
- A basic message whose Regarding it cannot decode, or whose form does not
  suit the conversation, is displayed as a reply to an unknown message.
- A message whose Editing it cannot decode is displayed as a new message, and
  marked as received as an edit of an unknown message. So is an edit whose
  original the receiver does not hold.

A reaction whose Regarding it cannot decode, or whose form does not suit the
conversation, has nothing to attach to and is not displayed. Nor is a message
that has no body and whose Message Type or Editing it could not interpret. A
message that is not displayed still holds its position in its sender's stream,
except a [Message Resend Request](#resend-request), whose Message Sequence
names a message in another stream.

## Message Type (0) {#message-type}

An empty or absent Message Type is type 0.

| Value | Name | Displayed as |
|---:|---|---|
| 0 | Basic text | A text bubble |
| 1 | Status text | A line of the form "*handle* *body*", as a user's action |
| 2 | [Message Resend Request](#resend-request) | Not displayed |
| 3 | [Message Unavailable](#unavailable) | Not displayed |

### Replies and Reactions {#replies-reactions}

A message that has a [Regarding](#regarding) option refers to an earlier one:

- A **reply** is a basic text message with Regarding. It is displayed as a
  message that answers the one it names.
- A **reaction** is a status text message with Regarding. It attaches to the
  message it names, and its body is the reaction.

A reaction's body is a short text token or an emoji. The tokens cover the
common reactions in one or two bytes, and a sender SHOULD use them:

| Reaction | Token | Also accepted |
|---|---|---|
| Approve 👍 | `+1` | 👍, in any skin tone |
| Disapprove 👎 | `-1` | 👎, in any skin tone |
| Love ❤️ | `<3` | ♥, ❤️ |
| Haha 🤣 | `ha` | `haha`, `lol`, 🤣 |
| Surprise ‼️ | `!` | `!!`, ‼️ |
| Question ❓ | `?` | ❓ |

A receiver accepts the spellings in the last column, and MAY accept other
common spellings of these reactions. It ignores ASCII letter case, and
treats any other body as the reaction of that body's first extended grapheme
cluster ([UAX #29](https://www.unicode.org/reports/tr29/)), so that a
sequence such as 👋🏽 or 🇫🇷 stays whole. It displays a reaction as that single
glyph.

A sender has at most one reaction in force on a message. A reaction with a
new body replaces its earlier one, and a reaction with no body withdraws it,
so a receiver displays the latest reaction it has from each sender.

A reaction refers to the original message's ID, even after the message has
been edited, as [Editing](#editing) requires. A receiver MAY also accept a
reaction that names an edit's own ID, by resolving it to the message the edit
replaced.

## Sender Handle (1) {#sender-handle}

A UTF-8 string, the name or pseudonym the sender goes by. When a message has
none, a receiver MAY use a name it holds for the sender, such as the one in
the sender's [identity](uep-0011.md#name).

## Message Sequence (2) {#message-sequence}

A **Message ID** numbers a message within its sender's stream in a
conversation. The option is optional, and a message without one cannot be
the subject of a reply, reaction, or edit, and cannot be
[repaired](#repair).

| Form | Value |
|---|---|
| 1 byte | `ID` |
| 3 bytes | `ID`, `INDEX`, `COUNT` |

- `ID`: the Message ID, shared by every fragment of a message.
- `INDEX`: a fragment's position from zero.
- `COUNT`: the number of fragments, at least 2. A receiver cannot decode a
  3-byte value whose `COUNT` is less than 2 or whose `INDEX` is not less than
  `COUNT`.

A sender numbers its messages in each conversation from its own counter,
increasing by one per message and wrapping from 255 to 0. A sender's
numbering in a conversation is independent of the numbering of anyone else in
it and of its own numbering in any other conversation. A sender that sends a
message again repeats its payload under the same ID, and a receiver that
already holds that ID in the stream displays one copy.

When an ID is reused after wrapping, the earlier message with that ID in the
same stream is retired: it is no longer the subject of a Regarding or an
Editing. Retirement affects no other stream and no message already displayed.

### Ordering {#ordering}

Message IDs compare by serial-number arithmetic modulo 256. Relative to the
most recent ID a receiver has accepted from a sender in a conversation, an ID
that is 1 to 127 ahead is newer, one that is 129 to 255 ahead is older, and
one that is exactly 128 ahead is ambiguous. An older message takes its place
in sequence order and does not become the most recent.

### Fragmentation {#fragmentation}

A message that fits a packet SHOULD NOT be fragmented. A longer one is split
into fragments, each in its own packet, by the 3-byte form.

- A fragment's body carries at most 160 bytes, and a message has at most 10
  fragments. A sender MUST NOT exceed either. A larger fragment or count is
  still valid on the wire, and a receiver that will not reassemble it drops
  the message.
- The body is split at byte boundaries. A fragment's body need not be valid
  UTF-8 on its own, and the receiver joins the fragments before it decodes
  the body, as [UEP-0003](uep-0003.md#strings) requires.
- The options of fragment zero apply to the whole message. A later fragment
  carries only Message Sequence, and a receiver ignores any other option it
  carries.
- A receiver SHOULD accept fragments in any order for at least thirty seconds
  after the first arrives, and MAY hold an incomplete message for up to two
  minutes. It marks where a fragment is missing in the text it displays.
- A receiver cannot present a fragmented message before it holds fragment
  zero, which carries its options. Until then it holds the fragments it has
  and displays nothing for the message.
- A receiver raises a notification for a fragmented message when its last
  fragment arrives, or after a bounded delay from the first if the message
  is incomplete.

## Sequence Reset (3) {#sequence-reset}

A flag that tells a receiver the sender has reset its Message ID counter in
this conversation, as when it has lost the counter. A receiver discards what
it holds about the sender's stream in the conversation: its recent IDs and
any fragments it is reassembling, unless the message bears an ID it already
holds, which is a repeat of that message and resets nothing. Other
conversations are unaffected.

A sender includes the flag with a Message Sequence that gives its new
starting ID. A receiver reads a flag without one as starting a new sequence
at the sender's next message.

A sender announces a reset on the next message it sends in the conversation,
and sends no message of its own to announce it.

## Regarding (4) {#regarding}

Names the message that a reply or reaction concerns. The form depends on the
conversation:

- **One-to-one conversation**: the two nodes number independently, so the form
  says whose message is meant.
  - 1 byte: the ID of a message sent by the recipient of this message.
  - 2 bytes: the ID of a message sent by the sender of this message,
    followed by `0x00`. A second byte of any other value cannot be decoded.
- **Group conversation**: 4 bytes. The ID, then the first 3 bytes of the
  address of the message's sender, its [node hint](uep-0004.md#node-hint),
  since members of a group number their messages independently.

A receiver MAY read a 1-byte Regarding that names none of its own messages as
naming one of the sender's.

A message can be named only while its ID is not retired, so a message more
than 255 messages old in its sender's stream, or one sent before the sender
reset its sequence, cannot be.

## Editing (5) {#editing}

Marks a message as replacing an earlier one in the same conversation from the
same sender. Its value is 1 byte, the ID of the message replaced. The sender
is the source of the packet, so it needs no prefix. For a multicast, that
source is a claim unless a frame signature attributes the message
([Conversations](#conversations)).

An edit with no body deletes the original.

An edit has its own Message ID. A later Editing or Regarding names the
original message's ID and never the edit's, so the original ID is the stable
reference.

A receiver that keeps the history of an edited or deleted message SHOULD keep
the original's identity, or a tombstone for it, so that references to it
still resolve. How edits are displayed, and whether earlier versions are kept,
is a matter for the implementation.

## Colors {#colors}

Background Color (6) and Text Color (7) each carry 3 bytes, red, green, and
blue, a color the sender suggests for the message's bubble and its text. A
receiver MAY ignore either, and one that applies them SHOULD ensure the text
remains legible against the background.

## Padding (9) {#padding}

A sender MAY add Padding of any length and content to conceal a message's
true length. A receiver ignores every instance and its value.

## Message Body {#body}

The body is a UTF-8 string, as [UEP-0003](uep-0003.md#strings) defines. A
receiver displays a body that is not valid UTF-8 with each invalid sequence
replaced, as that UEP describes.

### Group Invitations {#invitations}

A basic text message whose whole body, ignoring leading and trailing white
space, is a [group URI](uep-0019.md#group-uris) invites its recipients to that
group. A receiver that recognizes the URI MAY present the message as an
invitation to join. One that does not displays the body as text.

### Test Messages {#test-messages}

A basic or status text message on the [`EMERGENCY`](uep-0021.md#emergency)
group is a **test message** when its body, ignoring leading white space,
begins with `TEST:` in any ASCII letter case. For a fragmented message, the
body of fragment zero decides.

Unless a person has opted in to test messages, a receiver SHOULD NOT raise an
alert for one: no sound, vibration, notification, screen wake, or unread
indication. The message is still stored and displayed.

## Message Repair {#repair}

A receiver can notice that a message is missing from a sender's stream, and
ask the sender to send it again. Repair is optional: a sender need not answer
a request, and a receiver need not make one.

### Gaps and Baselines {#gaps}

A message that is more than one [ahead](#ordering) of the most recent ID
leaves a **gap**: the IDs between them are missing from that sender's stream.
A gap says nothing about any other sender in the conversation. A message that
is not displayed fills its position as any other does.

A message establishes a new **baseline** instead of a gap when it is:

- the first message a receiver sees from the sender in the conversation,
- the first message after a [Sequence Reset](#sequence-reset),
- ambiguous, or
- more ahead than the receiver repairs automatically
  ([Automatic Repair](#automatic)).

A receiver MUST NOT request messages to backfill across a baseline.

A repaired message belongs at its **sequence order** in its sender's stream,
not where it arrived. A receiver MAY reserve that position when it first sees
the gap, show a placeholder there while a repair is outstanding, and fill the
position in place when the message arrives, marking it as late if later
messages are already displayed. A gap that cannot be repaired, because
repair was exhausted, expired, or the sender disclaimed it, MAY be shown as
an unavailable position instead of being removed.

### Message Resend Request (Type 2) {#resend-request}

A **Message Resend Request** asks a sender to send a message again.

- It has one Message Type option, with value 2, and one Message Sequence
  option that names the frame wanted. A request whose Message Sequence is
  repeated is invalid and a receiver ignores it.
- It MAY have the [Group Resend](#group-resend) option, and SHOULD have no
  other option. A receiver validates these and then ignores every other option
  and the whole body. A sender SHOULD send an empty body.
- A request names one frame, and a response sends one frame. The 1-byte
  Message Sequence form names a message by ID without a fragment: the sender
  answers with the message if it was not fragmented, and with fragment zero if
  it was, whose fragment count lets the requester ask for the rest one
  fragment at a time. The 3-byte form names one fragment.
- A request arrives by unicast or by group unicast. A receiver discards one
  that arrives by multicast or broadcast, as a multicast request is not
  answered ([UEP-0008](uep-0008.md#group-traffic)).

### Group Resend (8) {#group-resend}

A flag with no value, used only on a request that arrives by group unicast. A
request for a message missed from a group conversation arrives by group
unicast, as does one for a message missed from a one-to-one conversation by
group unicast. The flag selects which: with it, the request concerns the
sender's group conversation, and without it, the one-to-one conversation
between the sender and the requester on that group.

A receiver discards a request that has the flag with a value, or that has it
and did not arrive by group unicast. On any other message the flag has no
meaning and a receiver ignores it.

### Responding {#responding}

A node answers a request, with the message or with Message Unavailable, only
for a Message ID it assigned recently in the conversation the request selects.

- A node MUST NOT answer a request for an ID it has not assigned. It SHOULD NOT
  answer one for an ID it assigned more than fifteen minutes earlier. It
  ignores such requests.
- An ID that a node assigned but never transmitted is answered with Message
  Unavailable, which closes the gap it left.
- A node that no longer has the message, because it deleted or evicted
  it, SHOULD answer with Message Unavailable.
- A node MAY coalesce requests for one frame, answering once.

A response travels the way the original conversation does. A request that
arrived by unicast is answered by unicast, and a request for a one-to-one
conversation that arrived by group unicast on a group is answered by group
unicast on that group, as [UEP-0005](uep-0005.md#response-carriage) requires.
A response to a request for the group conversation is sent by multicast to
the group, so that one response repairs every member that missed it.

A message that has been edited or deleted is answered with its current
content re-issued under its original ID, which for a deleted message is none,
so with Message Unavailable. A node MUST NOT send the content that an edit
replaced or a deletion removed, and this holds across restarts.
A node MAY keep the superseded content for its own use.

### Message Unavailable (Type 3) {#unavailable}

**Message Unavailable** tells a requester that the frame it asked for will
not come.

- It SHOULD have only the Message Type option, with value 3, and one Message
  Sequence option that matches the frame requested. Its body SHOULD be empty.
- A receiver that recognizes one with its single Message Sequence option
  ignores every other option and the whole body. It accounts for the position
  the message names, so that the position is no longer a gap.
- When the option names a fragment, only that fragment is unavailable. A
  receiver that is reassembling the message still repairs its other
  fragments, and SHOULD display the unavailable fragment as such and not as
  pending.

A response follows the same path as the message it stands for, as
[Responding](#responding) describes.

### Automatic Repair {#automatic}

A receiver MAY request each missing message of a gap, after a short grace
period for reordering, with a request in the 1-byte form. These limits apply:

- A receiver SHOULD NOT request more than eight missing messages automatically
  from one gap. A gap larger than that is a baseline.
- A receiver SHOULD limit the requests it sends to each peer, and overall.

A message whose fragments are missing is repaired fragment by fragment with
the 3-byte form, once its fragment count is known and a short quiet time has
passed since its last fragment arrived, so that a message being delivered is
not repaired.

A receiver that holds a gap at the original ID of an edited message MAY treat
an edit that names the ID as filling the gap, and cancel the repair, as the
edit already carries the position's current content.

#### Group Conversations {#group-repair}

A group member's request goes to the original sender by group unicast, which
needs the sender's full address. A member that holds only the sender's hint
cannot build the request and shows the loss.

Every member sees the same loss at about the same time, and one response by
multicast serves them all. A receiver therefore requests repair of a group
conversation automatically only under these rules:

- It MUST NOT unless it has itself sent a message in the conversation within
  the last 60 seconds.
- It MUST delay its first request by at least the time since that message,
  plus an independent random interval.
- It MUST cancel a request not yet sent when the missing message, or Message
  Unavailable for it, arrives in the group.
- It SHOULD NOT send more than two automatic requests for one missing message
  or fragment.

A receiver that does not repair a group gap automatically SHOULD let a person
ask for the missing message or fragment from its placeholder. That is one
request, sent only in answer to that action.

## Registry Considerations {#registry-considerations}

This UEP creates the [Text Message Types](registries/text-message-types.md)
and [Text Message Options](registries/text-message-options.md) registries.

- **Text Message Types**: values 0 to 255, allocated by a standards UEP. The
  registry reserves no experimental values.
- **Text Message Options**: values 0 to 65535, allocated by a standards UEP.
  Values from 60000 up are
  [experimental](uep-0001.md#experimental-values).

This UEP allocates types 0 to 3 and options 0 to 9, as defined above. Payload
type 3 is entered in the [Payload Types](registries/payload-types.md) registry
under this UEP.

## Security Considerations {#security-considerations}

**Claimed senders.** A multicast message names its source, and any member of
the group can name any other member. A reaction, edit, or deletion in a group
conversation is therefore attributed to its claimed source, and one member can
forge another's. An edit or deletion that a person must be able to trust in a
group conversation needs a frame signature. A unicast or group unicast is
authenticated to its source.

**Text from outside.** A handle, a body, and a color are chosen by the sender.
A handle can imitate another's, and bidirectional controls can make text
appear in an order other than its sender's. Two equal colors hide a message,
and two close ones strain its reader. A receiver treats these as the sender's
presentation, and a color as a suggestion.

**Resource use.** A fragmented message makes a receiver hold up to ten
fragments for up to two minutes. A receiver bounds the memory that unfinished
messages use, and discards the oldest when it must.

**A request makes a node transmit.** A resend request is the one text message
that does, so the rules of [Message Repair](#repair) bound it. A node answers
only IDs it assigned recently, an attacker cannot name an ID that was never
sent, and a node coalesces repeats and applies its own limits on the requests
it answers. A request by multicast is never answered, so one packet cannot
draw a response from every member of a group.

**Requests are authenticated, responses may not be.** A request arrives by
unicast or group unicast, so its source is authenticated. A response sent by
multicast to a group names its source only as a claim: any member can send
Message Unavailable for another member's message and close its gap on
receivers, which loses nothing a receiver could not have lost already, but can
keep a message from being repaired. A message with a frame signature is the
exception.

**Superseded content.** A node never sends content that an edit replaced or a
deletion removed, so a resend request is not a way to recover it.

**What a request reveals.** A request names a sender and an ID. A group member
that requests repair shows that it missed the message, and the rules for
group repair limit how many do.

**Invitations.** A group-key URI is the key
([UEP-0019](uep-0019.md#security-considerations)). A message that carries one
is as private as the message: a multicast, or a message that is not encrypted,
discloses the key to everyone who can read it.

**Test messages.** A body that begins with `TEST:` only withholds alerts about
that message, which a sender who could write on the group could choose
anyway. It does not make the message untrustworthy or change who may send it.
