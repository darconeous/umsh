This UEP defines forward secrecy sessions: a handshake through which two
nodes exchange ephemeral addresses, the traffic they then send between those
addresses, and how a session ends. Traffic sent during a session cannot be
decrypted by anyone who later obtains either node's long-term private key.

## Sessions {#sessions}

A **session** joins two nodes through a pair of **ephemeral addresses**, one
for each node. An ephemeral address is a node address
([UEP-0004](uep-0004.md#addresses)) whose keypair the node generates for one
session, holds only in volatile memory, and erases when the session ends. Its
keys are converted and agreed exactly as a long-term address's are
([UEP-0007](uep-0007.md#keys)).

The **initiator** asks for a session, and the **responder** answers.

Two nodes hold at most one session with each other. A session that is
established replaces any earlier one between the same two nodes.

## Handshake {#handshake}

1. The initiator generates an ephemeral keypair and sends a
   [PFS Session Request](#pfs-session-request) naming its ephemeral address
   and the duration it asks for.
2. The responder generates its own ephemeral keypair and sends a
   [PFS Session Response](#pfs-session-response) naming its ephemeral
   address and the duration it accepts.

Both messages travel between the two nodes' long-term addresses, under their
long-term keys. Each node then holds both ephemeral addresses and derives the
session's keys. No further setup is needed.

### Admission {#admission}

A responder MAY decline a request, and sends nothing when it does. A node
refuses a request or response that names an ephemeral address that is not a
valid address ([UEP-0007](uep-0007.md#address-validation)) or that it
already knows: one of its own addresses, a peer's, or one in another
session.

A request that repeats the request that opened a standing session, naming
the same ephemeral address, is answered with the same response again and
opens nothing.

### Confirmation {#confirmation}

The responder learns that its response arrived from either of:

- the MAC ack of the response, when the response requested one, or
- the first frame it receives from the initiator's ephemeral address,
  authenticated under the session.

Until one arrives, the responder receives under the session but sends
nothing under it, and goes on sending to the initiator under its long-term
keys.

### Crossed Requests {#crossed-requests}

When two nodes each send a request to the other before either receives a
response, the request whose ephemeral address is lower, compared as a
big-endian unsigned integer, stands. The node that sent it ignores the other
node's request. The other node abandons its own request and answers.

### Unwanted Responses {#unwanted-responses}

An initiator that receives no response abandons its request. A node that
receives a response it is not waiting for answers it with
[End PFS Session](#end-pfs-session) if it holds no session with the sender,
so that the responder drops its half. This covers a request that was
abandoned and a node that restarted after sending its request. A response
received while a session is held with its sender repeats the response that
opened the session, or is older than it, and is dropped.

## Session Traffic {#session-traffic}

Session traffic is [unicast](uep-0005.md#unicast) from one ephemeral address
to the other, secured with the two ephemeral addresses'
[pairwise keys](uep-0007.md#pairwise-keys). It is processed in every respect
as unicast between any two addresses, and any payload that unicast carries
may be sent under a session.

- **MIC size**: Session traffic SHOULD use a 4-byte MIC
  ([UEP-0007](uep-0007.md#mic-size)). The keys are erased when the session
  ends.
- **Attribution**: A node attributes traffic from its peer's ephemeral
  address to the peer's long-term address.
- **Frame counters**: Each ephemeral address draws its counters from its own
  sequence, as any address does ([UEP-0007](uep-0007.md#frame-counters)). A
  node SHOULD start that sequence at a random value.
- **Counter persistence**: A node does not persist an ephemeral address's
  counter or its peer's baseline. A restart ends every session the node
  holds, and the addresses are never used again.

## Session Lifetime {#session-lifetime}

The duration a request asks for and a response accepts is in minutes. A
sender MUST NOT send a duration of 0, and a receiver reads one as the longest
session it agrees to. A response's duration MUST NOT exceed the request's, so
read. Both nodes hold the session to the duration the response carries,
counted from when each holds both ephemeral addresses. Either node MAY end a
session sooner.

A session ends when:

- its duration runs out,
- either node sends [End PFS Session](#end-pfs-session), or
- a node gives up on its peer: a node SHOULD end a session when three
  consecutive frames it sends under the session with an acknowledgment
  requested go unacknowledged, and nothing from the peer under the session
  arrives in between. It then sends End PFS Session.

When a session ends, each node MUST erase the private key of its ephemeral
address. The ephemeral private keys MUST NOT be written to durable storage,
to logs, or to any other medium that outlives the session.

### Ending a Session {#ending}

A node sends End PFS Session under its long-term keys, after it holds no
session with the recipient. A node that lost a session, by restarting or
otherwise, can therefore still end it.

An End is carried the way the session's handshake was: by
[group unicast](uep-0005.md#group-unicast) on the group that carried the
handshake, or by unicast. A node that does not know how the handshake was
carried, or no longer holds that group's key, sends the End by unicast. An
End that answers an [unwanted response](#unwanted-responses) is carried as
[UEP-0005 §response-carriage](uep-0005.md#response-carriage) defines. A
receiver accepts an End by either carriage.

An End PFS Session sent under the long-term keys ends the session the
recipient holds with its sender only if its frame counter comes after, in the
modular comparison of [replay detection](uep-0007.md#replay-detection), the
counter of the sender's half of that session's handshake: the request the
recipient answered, or the response it accepted. An End that does not was
sent before the session began, and is ignored. A request still waiting for
its response is not ended by an End.

A node also accepts an End PFS Session from its peer's ephemeral address,
under the session's keys, and it ends that session.

### Retired Sessions {#retired-sessions}

A node that restarts loses its ephemeral private keys, and with them every
session it held. Its peer cannot learn this on its own, and goes on sending
under the session until its duration runs out.

To end such a session promptly, a node MAY keep, in durable storage, the
public half of each session it holds: its own ephemeral address, the peer's
ephemeral address, the peer's long-term address, the group that carried the
handshake, if any, and when the session expires. After a restart, a session
it holds such a record of is **retired**.

- A node keeps a retired session's record until its duration has passed, the
  session is ended, or a new session with the same peer replaces it. A node
  that cannot tell how much of the duration remains counts the whole
  duration from when it started.
- A node that receives a unicast or group unicast whose destination is a
  retired session's local ephemeral address, and whose source is the session
  peer's ephemeral address, discards it. The node holds no keys for the
  session, so it matches the packet by those addresses alone, without
  authenticating it. It SHOULD then send End PFS Session to the peer, and
  forget the record once that End is acknowledged. A node that hears no
  acknowledgment keeps the record, and the next such packet prompts another
  End. A node has at most one End for a retired session awaiting its
  acknowledgment at a time.

## Commands {#commands}

Each command is a [MAC command](uep-0006.md#encoding). All three are carried
by unicast and group unicast only.

### PFS Session Request (6) {#pfs-session-request}

Asks the destination to open a session.

| Field | Size | Description |
|---|---:|---|
| Ephemeral address | 32 bytes | The initiator's ephemeral address |
| Duration | 2 bytes | The session lifetime asked for, in minutes |

### PFS Session Response (7) {#pfs-session-response}

Answers a PFS Session Request, and is carried as
[UEP-0005 §response-carriage](uep-0005.md#response-carriage) defines.

| Field | Size | Description |
|---|---:|---|
| Ephemeral address | 32 bytes | The responder's ephemeral address |
| Duration | 2 bytes | The session lifetime accepted, in minutes |

### End PFS Session (8) {#end-pfs-session}

Ends the session between the sender and the destination. May be sent by
either node, including one that no longer holds the session.

End PFS Session defines no fields. It names the session by its sender, since
two nodes hold at most one session with each other.

## Security Considerations {#security-considerations}

### Forward Secrecy {#forward-secrecy}

A session's traffic is protected by keys derived from the two ephemeral
private keys. Once both are erased, nothing can rebuild them, and the
traffic cannot be decrypted even by an attacker who obtains both long-term
private keys. Traffic under the long-term keys has no such protection: anyone
who obtains either long-term private key can decrypt all of it, past and
future.

The protection rests on erasure. An implementation that lets an ephemeral
private key reach swap, a log, a crash dump, or freed memory that is not
overwritten loses forward secrecy for that session. On a platform without
virtual memory, this means explicitly zeroing the key before its memory is
released.

### Linkability {#linkability}

A session's packets carry hints of its ephemeral addresses, which appear only
for the session's duration. An ephemeral address cannot be told from a
long-term one.

The link between ephemeral and long-term addresses is still exposed in
several ways:

- **The handshake**: the handshake names both ephemeral addresses under the
  long-term keys. Sent unencrypted, it names them to every observer. Sent
  encrypted, it names them to an attacker who later obtains a long-term
  private key, who learns which long-term addresses opened the session,
  though not what it carried. A handshake carried by group unicast conceals
  the long-term addresses from nodes outside the group, and the End that
  closes the session follows it there.
- **Timing**: an observer who sees the handshake and then unfamiliar
  addresses appear on the air can link the two.
- **Frame counters**: an ephemeral address whose counters continue its
  long-term address's sequence links the two. A random starting counter
  removes that link.
- **MIC size**: the security control field is sent in the clear, so a 4-byte
  MIC marks a packet as likely session traffic, but not whose.
- **Retired session records**: anyone who can read a node's durable storage
  learns the long-term address behind each recorded ephemeral address.

### Handshake Authentication {#handshake-authentication}

The handshake and End PFS Session under the long-term keys are as authentic
as any unicast between the two nodes, so only the two nodes can open or end
a session between them. Knowing the ephemeral addresses lets no other node
send under the session, since the session's keys also require an ephemeral
private key.

An End is judged against the handshake's frame counters, so a delayed or
replayed End from before a session cannot end it.

A retired session matches packets without authenticating them, so anyone who
knows its two ephemeral addresses can prompt its node to send an End to the
peer. That End closes only a session its node has already lost, and a node
has at most one awaiting acknowledgment at a time.

### Resource Use {#resource-use}

Each request a responder accepts commits a session slot and a fresh keypair.
A responder that accepts every request lets any node that can reach it fill
its sessions. A responder may restrict whom it accepts requests from, and
how often.
