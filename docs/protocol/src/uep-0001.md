A UEP (UMSH Extension Protocol) is a numbered document that specifies one part of UMSH, including the
UMSH Local Control Protocol (ULCP) that devices speak to hosts. This UEP
defines how UEPs are proposed, numbered, written, and changed, and how the
numeric identifiers they allocate are recorded.

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY**
are to be interpreted as described in
[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and
[RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) when they appear in all
capitals.

## Types {#types}

- **Standards**: wire formats and behavior that an implementation follows.
- **Informational**: analysis or rationale. Nothing in it is a requirement.
- **Profile**: the set of UEPs that a kind of node implements, as a target an
  implementation can claim conformance to.
- **Process**: how UEPs work.

A standards UEP covers one feature: everything a node needs to implement it,
both on the air and over a local link. A feature that a local link configures
or controls defines its ULCP commands, properties, streams, and capability bit
in the same UEP as its behavior. The title of a UEP that specifies only ULCP
begins with `ULCP: `.

## Drafts {#drafts}

A proposal starts as a **draft**, named `draft-uep-<editor>-<title>-<NN>`:

- `<editor>` is the editor's handle, in lowercase.
- `<title>` is a short lowercase name, with words separated by hyphens.
- `<NN>` is the draft's [revision](#revisions), two digits starting at `00`.

The name without its revision identifies the draft across revisions. A draft
has no number, is edited in place, and may describe behavior that nothing
implements yet. A draft that is not pursued is marked `abandoned` and kept,
since registry entries and code may cite it.

## Numbers {#numbers}

A draft receives a number when the project accepts it. Its first numbered
version is published as an Experimental UEP. From then on, the number belongs
to that concept:

- A number is never reused, including after the UEP is withdrawn or
  superseded.
- A UEP is never deleted. Its status records what became of it.

A number is written with four digits and the prefix `UEP-`: `UEP-0019`.

Numbers are assigned in dependency order, so that a UEP makes normative
references only to UEPs with lower numbers. Where related UEPs refer to one
another, the more fundamental one takes the lower number, and the text that
closes the cycle moves into the later UEP. Informative references do not
constrain the order.

## Status {#status}

| Status | Applies to | Meaning |
|---|---|---|
| `draft` | Drafts | Proposed and edited in place |
| `abandoned` | Drafts | No longer pursued |
| `experimental` | UEPs | Accepted and numbered; edited in place |
| `final` | UEPs | Frozen |
| `active` | Process UEPs | In force and edited in place; never final |
| `withdrawn` | UEPs | No longer recommended, and replaced by nothing |
| `superseded` | UEPs | Replaced by the UEPs in `superseded-by` |

A final UEP does not change, apart from its `status` and `superseded-by`
fields. A change to it is made in a new UEP that lists it in `obsoletes`.

## Revisions {#revisions}

Each draft, and each UEP that is not final, carries a revision number. The
revision increases with any change to a wire format or to behavior that a peer
can observe, and stays the same for editorial changes. A UEP's revision starts
at 1 when it is numbered.

An implementation cites the revision it implements: `UEP-0019 rev 4`, or a
draft's full name including its revision.

## Header {#header}

A UEP or draft begins with a TOML header between two lines of `+++`. The
title is rendered from the header, so the body does not repeat it.

| Field | In | Value |
|---|---|---|
| `uep` | UEPs | The UEP's number |
| `name` | Drafts | The draft's name, without its revision |
| `title` | Both | The title |
| `type` | Both | `standards`, `informational`, `profile`, or `process`; for a draft, the type it would have |
| `status` | Both | A [status](#status) |
| `revision` | Both | The [revision](#revisions) |
| `requires` | Both | The UEPs, and for a draft also the drafts, this one makes normative references to. Optional |
| `see-also` | Both | UEPs and drafts referred to informatively. Optional |
| `obsoletes` | UEPs | The UEPs this one replaces. Optional |
| `superseded-by` | UEPs | The UEPs that replace this one. Optional |
| `draft` | UEPs | The draft this UEP was accepted from, without its revision. Optional |

## Structure {#structure}

The body opens with a paragraph stating what the UEP covers. The sections
below follow the specification itself, in this order, when they apply:

- **ULCP Interface**: the commands, properties, streams, and capability bit
  the UEP defines for controlling its feature over a local link.
- **Registry Considerations**: the registries the UEP creates and the values
  it allocates.
- **Security Considerations**: required in every standards UEP. It states
  what the UEP exposes or relies on, or that it changes nothing.
- **References**: the external documents the UEP cites.

**Appendices** follow, lettered in order: `Appendix A`, `Appendix B`, and so
on. Test vectors, required for each cryptographic construction or encoding the
UEP defines whose output is not evident from its description, go in an
appendix, as do long tables that support the text without being needed to
follow it.

Every heading that may be cited carries an explicit anchor (`{#ack-tag}`), so
a citation survives rewording. A citation names the UEP and the anchor:
`UEP-0007 §ack-tag`.

Every reference to another UEP or to an external document, such as an RFC,
links to it.

## Registries {#registries}

Numeric identifiers—packet types, options, payload types, MAC commands,
identity options, and ULCP commands, properties, streams, capabilities, and
status codes—are recorded in **registries** kept outside the series, so that
allocating a value never changes a final UEP.

- The UEP that defines a field creates its registry, stating the registry's
  fields, ranges, and allocation policy, and links to the registry under
  Registry Considerations. Once that UEP is final, a change to the policy is
  made in a UEP that updates it.
- A UEP lists every value it allocates under Registry Considerations, and the
  registry records each value with a reference to the UEP that defines it.
- Each registry is published as a page of the UEP book.
- When a UEP is superseded, the references of its registry entries move to
  the UEP that supersedes it.
- A value is never reused. A value whose UEP is withdrawn, or whose draft is
  abandoned, is marked deprecated and retired.

### Early Allocation {#early-allocation}

A draft that runs on nodes beyond its editor's own takes an **early
allocation**: a permanent value whose registry entry refers to the draft by
name. When the draft is numbered, the entry's reference moves to the UEP.

### Experimental Values {#experimental-values}

A registry with room for them reserves a range of **experimental values**, at
the end of its identifier space that costs the most to encode. A registry with
few values reserves none.

- Experimental values are not registered or owned. Two drafts may use the same
  one.
- A firmware or application release MUST NOT send or accept an experimental
  value.
- When a draft takes an early allocation or is numbered, the permanent value
  replaces the experimental one. No implementation accepts both.

## Repository Layout {#layout}

| Path | Contents |
|---|---|
| `docs/protocol/src/uep-NNNN.md` | UEPs, each named by its number alone |
| `docs/protocol/src/drafts/` | Drafts, each named `draft-uep-<editor>-<title>.md` |
| `docs/protocol/src/guide/` | Unnumbered material that describes the whole system |
| `docs/protocol/src/index.md` | The index of every UEP |
| `docs/protocol/registries/` | Registry data, one TOML file per registry |
| `docs/protocol/src/registries/` | One page per registry, rendered from its data |

When a draft is numbered, its file is renamed to the UEP's file name.
