This UEP defines how nodes are addressed: the address itself, how addresses
are shown to people and parsed back, and the short hints that stand in for
addresses on the wire.

## Addresses {#addresses}

A node's **address** is its 32-byte Ed25519 public key
([RFC 8032](https://www.rfc-editor.org/rfc/rfc8032)). The address is both the
node's identifier and its credential: knowing it is enough to reach the node
and to verify what the node sends.

## Presentation {#presentation}

An address is shown in one of two forms:

- **Base58**, the canonical form: exactly 44 digits, as defined in
  [UEP-0003 §base58](uep-0003.md#base58).
- **Base16**: exactly 64 hexadecimal digits, most significant first. A node
  shows them in lowercase.

A parser tells the forms apart by length. It accepts hexadecimal digits in
either case, and rejects input of any other length, input with a character
outside its form's alphabet, and base58 input whose value exceeds
2<sup>256</sup> − 1.

A [hint](#hints) stands in for an address only where the address itself is
not shown. Where a whole address is shown, no hint is shown with it.

## Hints {#hints}

A **hint** is the first bytes of an address, carried on the wire in place of
the whole address. Hints come in two sizes.

### Node Hint {#node-hint}

A **node hint** is the first three bytes of an address. It names a packet's
source or destination node.

### Repeater Hint {#repeater-hint}

A **repeater hint** is the first two bytes of a repeater's address. It names a
repeater along a packet's path.

### Matching {#matching}

A hint is a prefilter, not an identity. Many addresses share each hint, so a
match says only that a node might be the one named. A node whose node hint
matches a packet's destination hint MUST confirm that it is the destination by
processing the packet cryptographically before acting on it as the
destination. Nothing in UMSH depends on a hint being unique.

### Rendering Hints {#rendering-hints}

A hint is shown as the base58 digits it determines, so that what is shown is
a prefix of the base58 form of every address the hint matches:

1. Pad the hint to 32 bytes twice: once with `00` bytes and once with `FF`
   bytes.
2. Encode both padded values in [base58](uep-0003.md#base58).
3. Compare the two encodings digit by digit, up to the hint's **budget**: four
   digits for a node hint, three for a repeater hint.
4. Emit each digit on which the encodings agree. At the first digit on which
   they differ, emit `*` and stop.

Every digit before a `*` matches the base58 form of every address the hint
matches. A node hint therefore renders as at most four characters, and a
repeater hint as at most three. Across all possible hints, the rendered shapes
occur this often:

| Rendered shape | Node hints | Repeater hints |
|---|---:|---:|
| Four digits | 79.963% | — |
| Three digits | — | 11.560% |
| Three digits and `*` | 19.692% | — |
| Two digits and `*` | 0.340% | 86.916% |
| One digit and `*` | 0.006% | 1.498% |
| `*` alone | 0.0001% | 0.026% |

A hint renders as `*` alone when the addresses it matches begin with two
different base58 digits. The first digit of an address changes 17 times
across all possible addresses, so exactly 17 node hints and 17 repeater hints
render this way. [Appendix A](#bare-star-hints) lists them.

A rendered hint's shape does not always tell a node hint from a
repeater hint: the node hint `C3 34 93` and the repeater hint `C3 34` both render
as `E*`.

### Choosing a Keypair {#choosing-keypair}

An implementation that generates a keypair for a long-term identity SHOULD
discard the keypair, and generate another, if:

- its node hint renders with a `*`, or
- its repeater hint renders as a single digit and `*`, or as `*` alone.

A qualifying keypair's node hint renders as four digits that match its
address, and its repeater hint as at least two. Most repeater hints render with a
`*`, so a repeater hint is not required to render without one.

About 79% of keypairs qualify, so finding one takes 1.27 generations on
average:

| Generations | Chance of a qualifying keypair |
|---:|---:|
| 1 | 78.744% |
| 2 | 95.482% |
| 3 | 99.040% |
| 4 | 99.796% |
| 5 | 99.957% |

### Collisions {#collisions}

Hints collide: two nodes may share one. The chance that a population shares at
least one hint:

| Hint size | 50 nodes | 600 nodes |
|---|---|---|
| 1 byte | 99.4% | ~100% |
| 2 bytes (repeater hint) | 1.9% | 93.6% |
| 3 bytes (node hint) | 0.01% | 1.1% |

The sizes follow from where each hint is used:

- **Node hints** are compared by every node that hears a packet, across a
  whole regional network. A collision makes each node attempt the
  cryptographic processing of packets meant for the other, for as long as
  both identities exist. It costs computation, never reachability. The only
  way to end a collision is for one node to take a new keypair, which means
  its peers have to learn its new address, so node hints are sized to make
  that rare.
- **Repeater hints** name repeaters along a path, and only repeaters within
  radio range of a transmission act on them, so the population that matters
  is a local one. A collision makes an unintended repeater forward a packet.
  Duplicate suppression keeps each repeater from forwarding a packet more
  than once, so a collision adds traffic but causes neither loops nor
  misdelivery.

## Security Considerations {#security-considerations}

A hint carries no authority. An attacker can generate keypairs until one
matches any chosen hint, so a node never accepts a packet, attributes
traffic, or makes a routing decision on the strength of a hint match alone.

Discarding keypairs whose hints render poorly
([Choosing a Keypair](#choosing-keypair)) leaves about 79% of all keypairs,
which costs about a third of a bit of key strength.

A hint that stays the same over time lets observers link a node's traffic.
Concealing it is the role of blind unicast and of the ephemeral addresses of
perfect forward secrecy sessions.
