Expand description

Fixed properties of the device this session runs on.

Fields§

§dev_version: &'static str

PROP_DEV_VERSION string (without NUL terminator).

§dev_model: Option<&'static str>

PROP_DEV_MODEL string (without NUL terminator), naming the hardware this firmware runs on. None on a device with no fixed model—a simulator, or a board brought up before it has a name— and the property is then absent rather than empty.

§default_device_name: &'static str

Factory/post-reset value of PROP_DEV_NAME.

§mtu: u16

PROP_PHY_MTU; must not exceed [MAX_MTU].

§tx_preamble_symbols: u16

Transmit preamble used by the radio runner, for PROP_PHY_T_FRAME.

§sync_word: u16

The only sync word this firmware can use; PROP_PHY_LORA_SW sets must match it (v0 limitation).

§min_tx_power_dbm: i8

Lowest transmit power the radio supports, in dBm.

§max_tx_power_dbm: i8

Highest transmit power the radio supports, in dBm.

§freq_khz_min: u32

Tunable frequency range in kHz, inclusive.

§freq_khz_max: u32§defaults: RadioSettings

Post-reset radio settings. enabled is forced off on reset per the spec regardless of what this carries.

§default_duty_limit: u16

Post-reset PROP_PHY_DUTY_LIMIT.

§duty: &'static DutyLedger

The shared duty ledger. The session owns the limit’s lifecycle and records its own transmissions here, but the ledger is consulted by every radio client on the device (the device node’s TX path draws from the same budget), so PROP_PHY_DUTY_NOW reports the combined figure and PROP_PHY_DUTY_LIMIT bounds the combined airtime.

§battery: Option<BatteryFields>

None: not battery powered; CAP_BATTERY is absent and PROP_BATTERY is unknown. Some: the capability is advertised and the fields say which measurements the platform reports.

§battery_diagnostics: Fields

Optional diagnostic properties implemented by this board; no new capability.

§alert: Option<AlertConfig>

None: the board has no way to make itself conspicuous; CAP_ALERT is absent and PROP_ALERT is unknown. Some: the capability is advertised and the config carries the deadline.

§time: Option<TimeConfig>

None: the board keeps no wall clock; CAP_TIME is absent and PROP_TIME / PROP_TZ_OFFSET are unknown.

§gnss: Option<GnssConfig>

None: no GNSS receiver; CAP_GNSS is absent and the positioning properties are unknown. Meaningful only alongside time—see GnssConfig.

§illuminance: bool

Whether an ambient light sensor is fitted. When set, CAP_ILLUMINANCE is advertised and PROP_ILLUMINANCE samples on every read; otherwise the property is unknown.

§temperatures: bool

Enable both temperature properties only when environment hooks exist.

§display_motion_wake: bool

Orientation-qualified display wake; enabled by default when supported.

§display_brightness: Option<u8>

None: the screen’s brightness is not adjustable; CAP_DISPLAY_BRIGHTNESS is absent and PROP_DISPLAY_BRIGHTNESS is unknown. Some: the capability is advertised, and the value is the brightness after a reset.

§keyboard: bool

Whether the device has a keyboard of its own. When set, CAP_KEYBOARD is advertised and PROP_KEYBOARD_LIGHT and PROP_KEYBOARD_AIDS exist, lit and with every aid on after a reset; otherwise both are unknown.

§ble: bool

Whether the device has a Bluetooth transport it can make unreachable on demand. When set, CAP_BLE is advertised and PROP_BLE_ENABLED and PROP_BLE_LINK exist; otherwise both properties are unknown.

§ble_pairing: bool

Whether the platform manages its own Bluetooth bonds. When set, PROP_BLE_BOND_COUNT and PROP_BLE_PAIRING exist, and a write of zero to the count reaches the platform’s wipe; otherwise both properties are unknown and answer STATUS_PROP_NOT_FOUND. Meaningful only alongside ble.

Deliberately not a capability of its own. CAP_BLE is the only Bluetooth capability there is, and a host that wants to know whether this device manages its bonds asks for the count and reads the refusal—a question it has to be able to answer anyway, since any property may be refused by firmware older than the host.

§ble_pin: bool

Whether the device has a Bluetooth transport that pairs with a configured passkey. When set, PROP_BLE_PAIRING_PIN exists; otherwise it is unknown.

Separate from ble, which is about making the transport unreachable: one that is always reachable still pairs.

§wifi: Option<WifiConfig>

None: no Wi-Fi hardware; CAP_WIFI_SCAN and CAP_WIFI are absent and every Wi-Fi property is unknown. Some: the scan capability is advertised, and the station capability with it where [WifiConfig::station] says there is one.

§ip: Option<IpConfig>

None: no IP stack; CAP_IPV4 and CAP_IPV6 are absent and every IP property is unknown. Some: whichever families the config names are advertised.

Deliberately unrelated to wifi. A stack is not a link, and a device that gets its addresses over Ethernet or a modem has these properties and no Wi-Fi at all.

§bridge_client: bool

Whether the platform runs an autonomous bridge client.

§reboot: bool

Whether the platform can restart the hardware on command. When set, CAP_REBOOT is advertised and CMD_REBOOT reaches [Effect::Reboot]; otherwise the command answers STATUS_UNIMPLEMENTED, and so do CMD_DFU and CMD_FACTORY_RESET, which both end in a restart. Every firmware sets this; a session that is a process rather than a board must not.

§dev_identity: bool

Whether the device holds an identity of its own: a key, the device-identity channel and peer tables, and what is built on them—its advertised identity, administration over the mesh, and announcements. When set, CAP_DEV_IDENTITY, CAP_IDENT, CAP_ADMIN, and CAP_ADVERT are advertised. When unset, all four are absent, their properties are unknown, and CMD_ANNOUNCE answers STATUS_UNIMPLEMENTED. Every firmware sets this; a device that only carries its host’s traffic, such as a LAN virtual radio, need not. Required by mac_node.

§stats: Option<&'static StatsLedger>

The shared traffic ledger. None: the device keeps no counters; CAP_STATS is absent and the PROP_STAT_* properties are unknown. Some: the capability is advertised and the counters are read and cleared through it.

Shared for the same reason the duty ledger is—the session is one of several radio clients and none of them sees the whole picture—and read straight out of encode_prop rather than fetched through an effect, because a host asks for all of these at once and nine deferred round trips to answer one screen would be absurd.

The four counters the MAC feeds ([Counter::needs_node]) additionally require mac_node.

§mac_node: bool

Whether a mesh node runs behind this session—a MAC of the device’s own that can repeat and that a backhauled host can sit point-to-point behind. Every firmware sets this; a simulated device with no node behind it must not, or it would advertise CAP_MAC_BACKHAUL while the backhaul switch connects the host to nothing. When unset, CAP_REPEATER and CAP_MAC_BACKHAUL are absent and the repeater and backhaul properties are unknown.

§meshcore_forwarder: bool

Whether the platform runs a MeshCore forwarder beside its node. When set, CAP_MESHCORE_FORWARDER is advertised and the MeshCore properties exist; otherwise they are unknown. Meaningful only alongside mac_node, whose repeater it shares.

§lan_bearer: LanBearerRole

Whether and how the platform runs a LAN bearer: beside its node, sharing its forwarding, or as the device’s PHY. Anything but LanBearerRole::None advertises CAP_LAN_BEARER; which properties and counters exist follows the role.

§i2c_buses: &'static [BusInfo<'static>]

The I2C buses a host may drive directly, as PROP_I2C_BUSES reports them. Empty: CAP_I2C is absent, the two I2C properties are unknown, and CMD_I2C_TRANSFER and CMD_I2C_SCAN answer STATUS_UNIMPLEMENTED. A bus’s max_data and max_ops are clamped to [I2C_DATA_MAX] and [I2C_MAX_OPS], which bound the session’s staging.

§i2c_devices: &'static [DeviceInfo<'static>]

Cached peripheral inventory, populated from startup identification or board knowledge before constructing the session. Reading PROP_I2C_DEVICES only encodes this slice; it never probes a bus.
